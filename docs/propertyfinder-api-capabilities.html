Authentication & Authorization

Lets us: get a token and control exactly which of the other tabs our integration is allowed to touch.

POST/v1/auth/token — get an access token

Credentials (API Key + API Secret) come from PF Expert → Developer Resources → API Credentials → generate type API Integration. Keys last up to 365 days; once a new key is generated the old one stops working.

POST https://atlas.propertyfinder.com/v1/auth/token
{ "apiKey": "...", "apiSecret": "..." }

200 →
{ "accessToken": "...", "expiresIn": 1800, "tokenType": "Bearer" }

No refresh token flow. Tokens expire in 30 minutes flat — the client must call this endpoint again on expiry, every time. Budget for this in any long-running worker.

Scopes — what a token can actually see

Always on (default)Opt-in (request when generating the key)
compliances:read
listing_verification:full_access
locations:read
projects:read
webhooks:full_access 		users:read / users:full_access

Having a valid token is not enough — the endpoint also checks the token's scope. Missing scope → 403 Forbidden, not a silent empty response. For our use case, we need at minimum leads:read and webhooks:full_access.

Leads

leads:read

Lets us: pull every enquiry submitted against our listings, including the enquirer's phone/WhatsApp/email — read-only.

GET/v1/leads — list & filter enquiries

ParamNotes
pagedefault 1
perPage1–50, default 50
projectIdfilter to one project
senderWhatsappUsernamefind every lead from one WhatsApp contact
listingSearchfilter by listing

Lead object — every field

FieldDescription
idLead identifier
listing.id, listing.referenceWhich listing triggered the enquiry
messageThe actual enquiry text the lead typed
sender.contacts[]Array of { type, value } — type is phone, email, or whatsappUsername
responseLinkDeep link into PropertyFinder's own inbox UI (not an API action)
createdAt, updatedAtTimestamps

Read-only. There is no endpoint to reply to, close, or send anything to a lead through PropertyFinder. responseLink just opens their web inbox for a human to use.

Webhooks

webhooks:full_access

Lets us: get pushed a notification the instant something happens, instead of polling — this is what makes real-time lead capture possible.

Subscription management

  • POST/v1/webhooks — subscribe to an event type (eventId + delivery config)
  • GET/v1/webhooks — list active subscriptions
  • DELETE/v1/webhooks/{eventId} — unsubscribe

Every event type available

CategoryEventsNeeds scope
Leadslead.created, lead.updated, lead.assignedleads:read
Listingslisting.published, listing.unpublished, listing.action, listing.publishFailedlistings:read
Usersuser.created, user.updated, user.deleted, user.activated, user.deactivatedusers:read
Public profilepublicProfile.verification.approved, publicProfile.verification.rejectedusers:read

The lead.* events deliver the same lead object shape documented in the Leads tab above. Signature verification and retry policy for failed deliveries aren't spelled out in the docs — treat delivery as best-effort and make your handler idempotent (dedupe by lead.id).

Also useful: subscribing to listing.published/listing.publishFailed is the documented way to confirm a publish actually succeeded, since POST /v1/listings/{id}/publish returns 200 immediately without waiting for the real result.

Listings

listings:read / listings:full_access

Lets us: create, edit, publish, unpublish, price-check and upgrade property listings programmatically — full listing lifecycle management.

Endpoints

CallDoes
POST/v1/listingsCreate a new listing in draft mode
GET/v1/listingsSearch/list listings, paginated, filterable by permit number, search term, status
PUT/v1/listings/{id}Update a draft or published listing (partial body); 409 if the state disallows edits
DELETE/v1/listings/{id}Delete a listing entirely
GET/v1/listings/{id}/publish/pricesCheck the credit cost of publishing before you commit
POST/v1/listings/{id}/publishKick off publishing (async — 200 ≠ live, confirm via webhook or re-fetch)
POST/v1/listings/{id}/unpublishTake a live listing down
GET / POST/v1/listings/{id}/upgradesList or apply paid boosts/features to a listing

What a listing record actually contains

  • Identity/status: id, reference, status, timestamps
  • Property facts: category (residential/commercial), type (apartment, villa, office-space, land…), size, builtUpArea, bedrooms/bathrooms, furnishingType, finishingType
  • Pricing: price.type (sale/yearly/monthly/weekly/daily), price.amounts, downPayment (sales)
  • Location & legal: location.id/coordinates, uaeEmirate, compliance (permit + license number — mandatory for UAE/KSA)
  • Media: media.images[] — needs a hosted, HTTPS, ≥7-day-valid URL PropertyFinder can fetch from its own egress IPs
  • Copy: localized title/description (en/ar) — no emojis or HTML in description yet
  • Amenities/enhancements: allowed values depend on property type + category + country combination

Region-specific compliance built into this tab

  • Dubai: DLD permit validation mandatory (except DIFC/JAFZA); listing type/projectStatus must map to the permit's official classification.
  • Abu Dhabi: ADREC compliance mandatory; sale vs. rent permit type must match listing category; manual verification with documents required after creation.
  • Saudi Arabia: REGA data is authoritative — PropertyFinder silently overrides your submitted category, type, size, location, and price fields with REGA's own record.

Not relevant to lead outreach directly, but this is the tab we'd use if we ever wanted to auto-publish or auto-price listings — currently out of scope for this project.

Users, Roles & Public Profiles

users:read / users:full_access / roles:read

Lets us: manage agent accounts, their public-facing profile (the one leads see on a listing), and their role/permission level on the PropertyFinder side.

Users

CallDoes
POST/v1/usersCreate a user + their public profile. Requires email, first/last name, mobile, roleId.
GET/v1/usersSearch users by status/role/profile/email, paginated
PATCH/v1/users/{id}Update name, email, mobile, role, active status (password update is deprecated/no-op)

Public Profiles

CallDoes
PATCH/v1/public-profiles/{id}Update the public-facing card: name, phone, whatsappPhone, bio, position, photo, LinkedIn, nationality, languages, compliance credentials
POST/v1/public-profiles/{id}/submit-verificationSubmit phone + license document for PropertyFinder to verify the agent

Note: the public profile's own whatsappPhone field is what a lead sees/uses to reach the agent from the listing page in the first place — worth keeping in sync with whichever number is actually wired into our Baileys/360dialog pipe.

Roles

GET/v1/roles — lists base + custom roles (id, name, roleKey, baseRoleKey, isCustom). Example: Admin, Agent, Decision Maker.

Credits

credits:read

Lets us: check how much publishing budget is left and audit what it's been spent on. Read-only, no way to top up via API.

CallDoes
GET/v1/credits/balanceCurrent available credit balance
GET/v1/credits/transactionsTransaction history — filter by date (max 90-day window) and type
GET/v1/credits/spentCredits spent, filterable per listing

Publishing a listing and applying upgrades are what consume credits.

Compliances

compliances:read (default on)

Lets us: look up a permit/license number against the government registry (DLD/ADREC/REGA) and get back the official, authoritative property record.

GET/v1/compliances/{permitNumber}/{licenseNumber} (also takes permitType) returns property.listingType (Unit/Villa/Building/Land), property.saleType (Primary/Secondary), and builtUpArea — these map directly onto listing fields like category, type, projectStatus.

Listing verification is automatically triggered after a listing is published, using this same data source.

Locations & Projects

locations:read / projects:read (default on)

Lets us: resolve a free-text area name into PropertyFinder's canonical location tree, and fetch a developer project's details.

CallDoes
GET/v1/locationsSearch locations by text (e.g. "Marina") or by parent — returns id, name, lat/lng
GET/v1/projects/{id}Fetch a developer project's details (used for project-level permits/bulk listings)

PropertyFinder explicitly recommends a human confirm the matched location rather than auto-selecting the top search result, to avoid mis-assigning a listing to the wrong area.

Rate Limits & Error Format

Lets us: know how hard we can hit the API and how to parse a failure programmatically.

  • POST /v1/auth/token: 60 requests/minute
  • Every other endpoint: 650 requests/minute (per IP + per client)

Errors follow an RFC-9457-style shape: type, code, title, status, detail, trace_id, plus a per-field errors[] array with JSON Pointers for validation failures.

StatusMeaning
400Malformed request/schema
401Missing/invalid token
403Valid token, missing scope
409Listing state conflict (e.g. editing something not editable)
422Business-rule validation failure
429Rate limit hit

What this means for our WhatsApp lead-outreach automation

  1. Capture is real-time and fully automatable. Subscribe to lead.created (Webhooks tab) → the instant someone enquires on a listing (Listings tab), we get their name, phone/WhatsApp-username/email, which listing, and their exact message — no polling required.
  2. The WhatsApp handoff is the whole play. sender.contacts[].type === "whatsappUsername" (or phone) from the Leads tab is exactly what's needed to open a WhatsApp conversation. This slots straight into this project's existing pipe seam: { agentId, leadNumber, direction, text, timestamp }. A new PropertyFinder lead becomes a synthetic "first inbound message" event feeding the same brain that already handles Baileys/360dialog messages.
  3. We cannot auto-send anything through PropertyFinder itself — there is no reply/send endpoint anywhere in this API (confirmed across the Leads tab). This lines up with this project's hard rule that the bot never messages a lead directly: the agent still manually opens WhatsApp and sends the first message, using the lead's own message field as the seed for the bot's suggested opener.
  4. Polling fallback exists if webhook delivery ever proves unreliable: GET /v1/leads?senderWhatsappUsername=... can reconcile or backfill missed events.
  5. The public profile's whatsappPhone field (Users tab) is what a lead actually taps to message the agent from the listing page — keep it pointed at whichever number is wired into our read pipe, or leads will be messaging a number we can't see.
  6. Nothing here bypasses WhatsApp's 24-hour session / template rule. A brand-new PropertyFinder lead is not yet an open WhatsApp conversation — the agent still has to be the one who sends the first message to start that window.
